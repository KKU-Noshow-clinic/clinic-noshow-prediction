# คำถามตรวจสอบหัวข้อ (5 ข้อ)

ตัวเลขอ้างอิงจาก `docs/ai_project_canvas.md`, `docs/model_results.json`,
`docs/loadtest_report.md` และ `docs/pipeline_handoff.md`

## 1. ถ้าโมเดลทำนายผิด ใครเดือดร้อน และเดือดร้อนอย่างไร

| ความผิดพลาด | ใครเดือดร้อน | ผลกระทบ |
|---|---|---|
| **False Negative** — ทำนายว่ามา แต่ไม่มา | คลินิก, แพทย์, ผู้ป่วยคนอื่นที่รอคิว | สล็อตแพทย์ว่างเปล่า เสียรายได้และเวลาบุคลากร ผู้ป่วยที่ต้องการนัดต้องรอนานขึ้น |
| **False Positive** — ทำนายว่าไม่มา แต่มา | ผู้ป่วย, ฝ่ายนัดหมาย | เสียค่า SMS/เวลาโทร ผู้ป่วยอาจรำคาญ ถ้าใช้ overbook อาจเกิดคิวล้น |

FN แพงกว่า FP มาก ทีมจึงเลือกโมเดลที่เน้น **no-show recall** (test 0.755) แลกกับ precision ต่ำ (0.284)
และกำหนดว่าผลทำนายใช้เพื่อ **เพิ่มการเตือน** เท่านั้น ห้ามใช้ตัดสิทธิ์หรือลดลำดับคิวของผู้ป่วย
เพราะจะกระทบกลุ่มเปราะบางที่โมเดลให้คะแนนเสี่ยงสูงอย่างไม่เป็นธรรม

## 2. ตัวชี้วัดทางธุรกิจคืออะไร และเชื่อมกับตัวชี้วัดของโมเดลอย่างไร

| ตัวชี้วัดธุรกิจ | ตัวชี้วัดโมเดลที่เชื่อม | เหตุผล |
|---|---|---|
| % ของนัด no-show ที่ได้รับการเตือนทัน | **Recall** คลาส no-show (**optimizing metric**, gate ≥ 0.60) | recall = สัดส่วนผู้ที่จะไม่มาที่ระบบจับได้ |
| ค่า SMS/เวลาโทรต่อ no-show 1 รายที่จับได้ | **Precision** (ติดตาม ไม่ใช่ gate) | precision 0.28 → เตือน ~3.5 คนต่อ no-show จริง 1 ราย |
| อัตราการใช้สล็อตแพทย์ | Recall × อัตราที่การเตือนทำให้ผู้ป่วยมา/ยกเลิกล่วงหน้า | ยกเลิกล่วงหน้าทำให้นำสล็อตไปให้คนอื่นได้ |
| คุณภาพการจัดอันดับความเสี่ยงโดยรวม | **PR-AUC** (gating ≥ baseline 0.299) | ไม่ขึ้นกับ threshold และเหมาะกับข้อมูลไม่สมดุล |

**หลักการเลือกโมเดล:** เลือกโมเดลที่ recall สูงสุดในกลุ่มที่ผ่าน gating ทั้งหมด → Exp 2 (LightGBM balanced)
เพราะในโจทย์นี้การพลาด no-show (FN) แพงกว่าการเตือนเกิน (FP)

บน test set (no-show 18.5%) โมเดลจับ no-show ได้ 75% และในทุก 100 คนที่เตือน มี 28 คนที่เสี่ยงจริง
เทียบกับการเตือนแบบสุ่มที่ได้ ~18 คน (lift ≈ 1.54)

## 3. ข้อมูลจะเปลี่ยนไปตามเวลาอย่างไร (Data Drift / Concept Drift)

**Data drift** (การกระจายของ features เปลี่ยน แต่ความสัมพันธ์กับ label เหมือนเดิม):
- ฤดูกาลและวันหยุด: lead time และวันในสัปดาห์ของนัดเปลี่ยน เช่น ช่วงไข้เลือดออกระบาดมีนัดด่วนมากขึ้น
- ประชากรผู้ป่วยเปลี่ยน: อายุเฉลี่ยสูงขึ้น, เปิดสาขาใหม่ทำให้มี `Neighbourhood` ใหม่
- นโยบายคลินิก: เริ่มส่ง SMS ให้ทุกคน ทำให้ `SMS_received` เกือบเป็น 1 ทั้งหมด

**Concept drift** (ความสัมพันธ์ระหว่าง features กับการมาตามนัดเปลี่ยน):
- ผู้ป่วยชินกับ SMS จนไม่ได้ผล ทำให้ `SMS_received` ไม่ได้ลดโอกาส no-show อีกต่อไป
- มีระบบขนส่ง/telemedicine ใหม่ ทำให้ lead time ยาวไม่ได้แปลว่าเสี่ยงเหมือนเดิม
- เหตุการณ์ภายนอก เช่น โรคระบาด ทำให้พฤติกรรมการมาตามนัดเปลี่ยนทั้งระบบ

**การตรวจจับ:** data drift ใช้ Evidently เทียบกับข้อมูล train; concept drift ต้องรอ label
(รู้ผลหลังวันนัด) แล้ววัด recall/PR-AUC ย้อนหลัง จำลองไว้ใน `scripts/make_drift.py`

## 4. ต้องตอบกลับเร็วแค่ไหน และรองรับปริมาณคำขอเท่าใด

- **งานหลักเป็น batch:** รันคืนก่อนวันนัดผ่าน `/predict_batch` (1–1000 นัดต่อคำขอ)
  คลินิกขนาดกลางมีหลักร้อยถึงพันนัดต่อวัน จึงไม่ต้องการความเร็วระดับมิลลิวินาที
- **Real-time:** ใช้ตอนเจ้าหน้าที่จองนัด ต้องตอบเร็วพอไม่ให้รู้สึกช้า กำหนด SLO
  **p50 ≤ 50 ms, p95 ≤ 200 ms, error ≤ 1%, availability ≥ 99%**
- **ผล load test** (Locust, 50 concurrent users, 2 นาที, วัดในเครือข่าย Docker):
  p50 **45 ms**, p95 **80 ms**, p99 120 ms, **142.5 req/s**, error 0% ผ่านทุก SLO
  (ใช้ uvicorn 2 workers + micro-batching 32 จากเดิม 1 process รับได้ ~36 req/s)
- 142 req/s เกินความต้องการของคลินิกหลายเท่า เผื่อรองรับหลายสาขาได้

## 5. ถ้าโมเดลเวอร์ชันใหม่แย่กว่าเดิม ระบบจะรู้และย้อนกลับอย่างไร

**ก่อน deploy — ป้องกัน:**
1. Pipeline register โมเดลใหม่เป็น alias `challenger` ใน MLflow registry `clinic-noshow`
2. Model gate ประเมิน challenger และ champion บน validation ชุดเดียวกัน
   ต้องผ่าน recall ≥ 0.60, PR-AUC ≥ baseline, ขนาด ≤ 100 MB และ **ต้องดีกว่า champion**
3. ไม่ผ่าน gate → ไม่ promote, แจ้งเตือนใน Discord, champion เดิมให้บริการต่อ
4. CI job `model-gate` ตรวจซ้ำก่อน merge

**หลัง deploy — ตรวจจับ:**
- Grafana: latency, error rate และสัดส่วนนัดที่ถูก flag เปลี่ยนผิดปกติ
- Monitoring: recall บน label จริงหลังวันนัดต่ำกว่าเกณฑ์ → alert

**ย้อนกลับ:**
- ตอน promote ระบบเก็บเวอร์ชันเดิมไว้เป็น alias `previous_champion`
- สั่ง `uv run python -m noshow.registry.rollback` เพื่อย้าย `champion` กลับไปเวอร์ชันก่อนหน้า
  แล้ว reload API ทันทีโดยไม่ต้อง rebuild container (ทดสอบแล้ว: API เปลี่ยน version 2 → 1)
- ข้อจำกัด: ยังไม่มี automatic rollback ต้องสั่งด้วยคน
